- Status: Done

- Status: Done
- Summary: Replaced `HybridRecommendationEngine`'s Sprint 20 fixed weighted-merge with a pluggable ranking-strategy architecture, per this Sprint's "production-quality ranking framework" goal, and extended it to a third signal (ALS) that Sprint 25 deliberately deferred.
  - **`domain/ranking_strategy.py`** (new): `RankingCandidateList` (a source name + one engine's already-ranked items) and the `RankingStrategy` port (`fuse(candidate_lists, limit) -> list[RecommendationItem]`) — a pure Domain abstraction with no Infrastructure knowledge, so `HybridRecommendationEngine`/the Application layer never change when a new fusion algorithm is added.

## Sprint 27 — Recommendation Re-ranking

### Task 1 — Recommendation Re-ranking Framework

- Status: Done
- Summary: Added a dedicated re-ranking stage executed after Hybrid ranking, kept fully independent of `RecommendationEngine` per the Sprint brief ("RecommendationEngine remains responsible only for candidate generation").
  - **`domain/reranker.py`** (new): `RerankingContext` (currently just an optional `user_id`, deliberately not carrying which engine produced the candidates — coupling reranking to a specific engine is exactly what this stage must avoid), the `RerankingPolicy` port (`apply(items, limit, context) -> items`), the `RecommendationReranker` port (`rerank(items, limit, context) -> items`), and `DefaultRecommendationReranker` — the reference implementation, composing an ordered `list[RerankingPolicy]` and chaining each policy's output into the next, truncating to `limit` only at the very end. Adding/removing/reordering policies is a construction-time (Composition Root) concern only, satisfying "policies must be composable... without changing Application logic."
  - **`domain/reranking_policies.py`** (new): three independent policies, at least one of each required kind.
    - `MMRDiversityPolicy` — Maximal Marginal Relevance-style diversification: iteratively selects the candidate that best balances (via a `lambda_param` dial) its own min-max normalized relevance against similarity to items already selected, rather than a plain score sort. Similarity defaults to a same-category proxy (a `Callable[[Book, Book], float]` — swappable without changing the policy's selection logic) so this policy has zero Infrastructure/embedding dependency, consistent with how category is already used as a similarity proxy elsewhere (`ranking_strategies.py`'s tie-breaks, the demo's evaluation ground truth). Deterministic tiebreak by book id, matching `ranking_strategies.py`'s existing convention.
    - `NoveltyBoostPolicy` — boosts items the context's `user_id` hasn't already interacted with (`UserBookInteractionRepository.list_by_user`), a no-op without a `user_id`. Complements ALS (which already excludes a user's own history from its own candidates) by extending that benefit to Popularity/Semantic candidates too, which have no per-user knowledge at all.
    - `PopularityPenaltyPolicy` — multiplies each item's score by `(1 - penalty * normalized_loan_count)`, damping over-exposure of already-popular items (`BookPopularityRepository`). Deliberately does **not** reuse the shared "all-equal-scores collapse to 1.0" min-max convention when every candidate's loan_count is 0 (no popularity signal for this call at all) — that would apply the *full* penalty to everyone precisely when there's no signal to justify penalizing anyone, so this case is special-cased to no penalty instead (caught by a test during development: `test_popularity_penalty_treats_unrecorded_popularity_as_zero` initially failed under the naive shared-helper reuse).
    - **Port extension**: `BookPopularityRepository` gained `get_by_book_id(book_id) -> BookPopularity | None` (both `InMemoryBookPopularityRepository` and `PostgreSQLBookPopularityRepository`) — the only way to look up a specific candidate's popularity; the existing port only supported `top_by_loan_count`, insufficient for penalizing arbitrary re-ranking candidates.
  - **`infrastructure/reranked_recommendation_engine.py`** (new): `RerankedRecommendationEngine(RecommendationEngine)` wraps any inner `RecommendationEngine` + a `RecommendationReranker`. Over-fetches `query.limit * candidate_multiplier` (default 3x) candidates from the inner engine before delegating to the reranker — re-ranking (MMR in particular) needs a genuine pool larger than `limit` to select a diverse subset *from*; reranking an already-`limit`-sized list can only reorder it. Implements the `RecommendationEngine` port itself rather than being a special-cased branch inside `HybridRecommendationEngine` or any use case — this is *how* re-ranking stays "an independent stage": the existing Evaluation Framework, `ApplicationContext` wiring, and Application-layer use cases all work with a reranked pipeline exactly as they would with any other engine, with zero framework changes required.
  - **`application/generate_reranked_recommendation_use_case.py`** (new): `GenerateRerankedRecommendationUseCase`, mirroring `GenerateHybridRecommendationUseCase`'s exact shape (`execute(limit, book_id=None)`) — it has no knowledge that its injected engine happens to be a `RerankedRecommendationEngine`, only the `RecommendationEngine` port.
  - **Evaluation Framework extension**: added `diversity_at_k(categories, k)` to `domain/evaluation_metrics.py` — relevance-independent (no `relevant` argument, unlike every other metric here): the fraction of distinct categories among the top-k, i.e. what the dimension re-ranking's `MMRDiversityPolicy` specifically targets.
